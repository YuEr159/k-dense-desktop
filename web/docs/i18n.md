# 中文界面

界面汉化用的是**运行时文本替换**，不是组件内的 `t()` 调用。这个选择来自一个具体约束：上游仓库（`K-Dense-AI/k-dense-byok`）是这份代码的事实来源，我们定期合并它。每个写进组件的 `t("...")` 都是一行上游可能同时改动的代码，翻译得越多，合并冲突越多。运行时替换让上游合并和我们之间几乎没有交集。

## 工作方式

`src/lib/i18n/` 下三块：

| 文件 | 作用 |
|---|---|
| `runtime-translate.ts` | 匹配器与 DOM 遍历，纯函数，可单测 |
| `locale-provider.tsx` | 挂在根布局上的 `MutationObserver` |
| `locale.ts` | 语言选择的读写（localStorage） |
| `zh-CN.json` | 唯一的翻译数据，键是英文原文 |

`LocaleProvider` 在 `<body>` 上观察新增节点和文本变化，把匹配到的文本节点就地改写。属性只处理 `placeholder` / `title` / `aria-label` / `alt`。

**永不改写**：`<pre>`、`<code>`、`<kbd>`、`<script>`、`<style>`、`<textarea>` 内部，以及任何带 `data-no-translate` 的子树。聊天消息容器（`MessageResponse`）带了这个标记——模型说的话不是界面文案，哪怕里面恰好出现 "File" 或 "Diff"。

## 为什么不用 i18n 框架

`next-intl` 之类的方案要在组件里包 `t()`，等于把界面文案的所有权从上游手里拿过来。上游每改一个带文案的组件，我们就多一处冲突。

代价是这套方案覆盖不到的东西：

- **被表达式打断的句子**。`There are {n} files` 在 DOM 里是三个节点，翻译单独的 `"There are "` 会产出碎掉的中文。采集脚本和运行时都跳过这类片段，它们保持英文——错误的翻译比未翻译更糟。
- **后端返回的文案**。`server/` 的 `detail`、错误消息、系统卡片不在前端树里。要覆盖得在后端做（未做）。
- **复数与词序**。`{0}` 模板能处理 `已连接（{0}）` 这种，但英文单复数变化（`1 skill` / `2 skills`）在中文里无差别，翻译时合并即可。

## 上游改动时会发生什么

不会冲突——`zh-CN.json` 是我们独有的文件。

上游改了一句文案，效果是那一句退回英文显示。这是**正确且可见**的降级：用户看到英文，不是看到错译或乱码。

同步上游后跑一次采集，看看新增了哪些：

```bash
cd web && node scripts/harvest-strings.mjs
```

它会重写 `zh-CN.skeleton.json`（空值骨架）。把它和 `zh-CN.json` 比对，新增的键就是待翻译项。`scripts/i18n-gaps.mjs` 用于补充 JSX 之外的来源：

```bash
node scripts/i18n-gaps.mjs --from gaps.json --write
```

## 怎么加翻译

1. 在 `src/lib/i18n/zh-CN.json` 里加一条，键**逐字**等于界面上显示的英文（含标点），值是中文。
2. 带插值的用 `{0}`、`{1}`；中文可以重排顺序，`{0}` 会填回原值。
3. 跑 `npx vitest run src/lib/i18n/` —— 字典完整性测试会检查空值、首尾空白、占位符数量不匹配。

不要翻译：品牌名（Kady、K-Dense、Modal、Ollama、LaTeX、MCP、Paperclip、Radius）、模型与提供商 ID、文件路径、环境变量名。

## 已知边界

- 语言切换会**重载页面**。逐节点还原试过，不可靠：React 拥有这些节点，它没有重渲染的那些会停留在旧语言，看起来像 bug。重载一次比半中半英诚实。
- 切换语言不影响对话内容——它们在服务端，或本来就带 `data-no-translate`。
- 翻译层不改变 `aria-label` 以外的无障碍语义，`lang` 属性会跟着切换。
